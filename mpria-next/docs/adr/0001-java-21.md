# ADR-0001 — Java 21 as the baseline runtime

* Status: Accepted
* Date: 2026-08-01

## Context

MpRIA v8 is pinned to Java 8 (Zulu 8.52) by Payara 5 and by the Vaadin 8 / Groovy-Eclipse
toolchain. The pin costs the team records, sealed types, pattern matching, the modern collections
and HTTP APIs, and — most importantly for a service architecture — virtual threads.

Java 21 and Java 25 are both LTS. Java 25 is installed on the dev machine alongside 21.

## Decision

Baseline on **Java 21** (`--release 21`), with the build's toolchain pinned so a developer with a
different default JDK still produces 21 bytecode.

## Rationale

* Java 21 is the widest-supported LTS: every container base image, every APM agent, every library
  we depend on supports it today without caveats.
* Virtual threads (JEP 444, final in 21) matter here specifically: `presentation-bff` fans out to
  four services per request. Platform-thread-per-request would need reactive code to scale;
  virtual threads let the fan-out stay blocking and readable.
* Records and sealed interfaces are the natural encoding for the presentation-model tree
  (`sealed interface LayoutNode permits Region, Slot, FieldRef`) — an exhaustive `switch` over the
  PM tree is compiler-checked.
* Java 25 offers little the domain needs beyond 21, and some ecosystem pieces (agents, bytecode
  tooling) still lag on a fresh LTS.

## Consequences

* No Java 25-only APIs. Enforced by `maven.compiler.release=21`, not by convention.
* **Upgrade trigger:** move to Java 25 once the OTel Java agent and Testcontainers both declare 25
  as fully supported, and no earlier than 12 months after its release. Expected to be a
  one-property change because we compile with `--release`.
* Groovy is not carried forward (see ADR-0005), so the Groovy-Eclipse compiler constraint that
  forced Java 8 disappears with it.
